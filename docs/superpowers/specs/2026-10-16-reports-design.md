# 汇报机制设计

日期：2026-10-16
适用版本：计划为 0.7.0（Claude 定）
关联：`docs/superpowers/specs/2026-09-22-cc-hub-design.md` §4.5（cron 任务定义）、§8（应用）；`docs/superpowers/specs/2026-10-12-cron-overrides-design.md`（时间覆盖）；`Jenwein/hub-apps` 的 `docs/superpowers/specs/2026-10-16-mail-design.md` §7（邮件对汇报的要求）

标注约定：没有标注的内容是用户的决定；标"（Claude 定）"的是 Claude 替用户做的选择，用户可以改；标"（留给实现者）"的由实现者决定。

## 1. 为什么

现在每个应用、每个后台任务都自己发消息：记忆整理半夜发一条，记账每月发一条提醒，计划应用早上一条、每周每月各一条回顾，邮件应用还要每天一份汇报。消息越来越碎，而且后台任务即使没什么可说的也要发一条。

cc-hub 提供一项公共能力：按周期（日、周、月、季、年）出一份报告，各个应用按周期往里加自己的内容，后台任务把结果留给下一份报告，不再各自发消息。

## 2. 目标、非目标、绝对不能出的错

**目标**

- 日报、周报、月报、季报、年报，每种都可配置、可选：单独开关、设发送时间。
- 应用声明给哪些周期供稿；供稿有两种方式：脚本命令（输出原样放进报告）和给 agent 的指示（agent 现写）。
- 任何任务都可以给下一份报告留言。
- 用户可以按应用关掉某个周期里的那一段。
- 报告存档在总站里。
- 汇总类的内容并进报告；必须在特定时间发、或要用户当场回应的（例如计划应用晚上问打卡、邮件的实时提醒）继续单独发。

**非目标**

- 用户自己写的报告段落（例如"日报里加天气"）（Claude 定：这次不做，用户可以让 agent 帮忙做成一个小应用）。
- 报告里的图片、文件附件（Claude 定：这次只发文字）。
- 发到多个聊天、多人报告。
- cc-hub 自己运行 agent：报告仍然由定时任务唤醒的 agent 来跑（§5）。

**绝对不能出的错**

1. 脚本类的段落被 agent 读到、改写或总结：它们必须原样到达用户，且不出现在 agent 能看到的输出里（邮件应用的安全要求）。
2. 发空报告：所有段落和留言都为空时不发任何消息。
3. 某一段出错却悄悄消失：出错的段落在报告里留一行说明。
4. 留言丢失：没有报告会带走留言时，任务照旧自己发消息（§6）。
5. 同一份报告发两次。

## 3. 周期和开关

每个周期是总站自带的一个定时任务，定义文件在 `cron/` 下，都是 `default: false`、`session: new_per_run`。开关和改时间直接用现有的 `cc-hub cron set`（时间覆盖存在 `hub.toml`），不新增配置方式。

| 任务 | 默认时间（Claude 定） |
|---|---|
| `report-daily` | 每天 08:00（`0 8 * * *`） |
| `report-weekly` | 周日 20:00（`0 20 * * 0`） |
| `report-monthly` | 每月 1 号 09:00（`0 9 1 * *`） |
| `report-quarterly` | 1、4、7、10 月 1 号 09:10（`10 9 1 1,4,7,10 *`） |
| `report-yearly` | 1 月 1 号 09:20（`20 9 1 1 *`） |

季报和年报错开十分钟，避免和月报同一分钟触发、消息顺序不定（Claude 定）。

例子：

```bash
cc-hub cron set report-daily --on
```
```bash
cc-hub cron set report-weekly "0 20 * * 5"
```
```bash
cc-hub cron set report-monthly --off
```

（第一条打开日报；第二条把周报改到周五 20:00；第三条关掉月报。改完照 `cron set` 打印的步骤在 cc-connect 里重新登记，和其他任务一样。）

- 默认全部关闭。首次设置总站时（`BOOTSTRAP.md`）问用户要开哪些报告、什么时间；装了供稿的应用时，`hub-apps` 的设置流程发现它供稿的周期还没开，问用户要不要打开（Claude 定）。
- cc-connect 每次触发定时任务时，默认先在聊天里发一行"⏰ <描述>"，除非登记时带 `--silent`。不去掉它，空报告和静默的后台任务仍然会留下这一行。所以 cc-hub 登记的所有定时任务（总站的和应用的）一律带 `--silent`（Claude 定）：登记命令和 `cron list --json` 的 `command` 随之改变，`hub-adapt` 和 `hub-apps` 比对已登记的任务时把是否 silent 也算进去，已登记的旧任务在下次比对时删掉重登。需要让用户知道"任务开始了"的应用，自己在回复里说。

## 3a. 语言

报告里由 cc-hub 写的文字（报告标题、段落标题、出错说明、留言的标题）直接到达用户，agent 没机会翻译，所以总站要知道用户的语言（Claude 定）：

- `hub.toml` 里加 `language`（例如 `zh-CN`），首次设置总站时问用户，已有总站在第一次打开报告时问。
- cc-hub 内置中文和英文的报告用语，其他语言先用英文。
- 脚本段从环境变量拿到这个语言，用它写自己的内容；指示段由 agent 用用户的语言写，和平时一样。

## 4. 应用怎么供稿

### 4.1 声明

应用在自己目录里放 `reports/<周期>.md`，周期是 `daily`、`weekly`、`monthly`、`quarterly`、`yearly` 之一（Claude 定，沿用 `cron/*.md` 的写法）：

- **脚本段**：frontmatter 里有 `command`，例如
  ```
  ---
  command: "uv run apps/mail/scripts/mailkit.py report daily"
  ---
  ```
  报告时由 cc-hub 在总站根目录运行这条命令（不经过 shell，按参数拆分，Claude 定），标准输出就是这一段的正文，原样放进报告。输出为空表示这次没有内容，这一段不出现。正文（frontmatter 以下）可以留空或写给人看的说明。
- **指示段**：没有 `command`，正文是给 agent 的指示（英文，和其他给 agent 读的文字一样）。报告时 agent 照着写这一段；写出来为空表示没有内容。

- 段落的标题统一由 cc-hub 加（用应用名，或应用在 frontmatter 里给的 `title`），应用的输出不用自带标题（Claude 定）。
- 脚本段运行时，cc-hub 通过环境变量告诉它周期、本期起止时间（上一份同周期报告的时间到现在；第一次为一个周期长度）（Claude 定，变量名留给实现者）。应用也可以自己记时间点（邮件应用就是这样）。
- 脚本段失败（退出码非零、超时）时，报告里这一段换成一行"<应用>的这一段出错了"和错误输出的第一行（Claude 定，超时时长留给实现者）。

### 4.1a 批准

cc-hub 原来的原则是"只搬文件，不执行"：从不运行应用提供的命令。脚本段是这条原则的唯一例外（用户定），条件是：

- 每条脚本段命令都要在这台机器上经用户批准才会被 cc-hub 运行。`hub-apps` 的设置流程把应用的报告命令逐条列给用户看、说明它做什么，用户同意后 agent 记下批准（例如 `cc-hub report approve <应用>`，命令名留给实现者）。
- 批准记的是命令的确切文字，存在每台机器自己的设置状态里（和 `setup-state` 放在一起，Claude 定）。应用升级后命令变了，设置流程重跑时重新问；`reports/` 的内容算进判断"设置是否要重跑"的依据。
- 报告时遇到没批准或批准后变了的命令，cc-hub 不运行它，这一段换成一行说明和批准的办法（Claude 定）。
- 指示段不需要批准：它是给 agent 读的文字，和应用的 skill 一样。

### 4.2 按应用关掉某一段

```
cc-hub report section <应用> <周期> --off
cc-hub report section <应用> <周期> --on
```

例子：

```bash
cc-hub report section ledger monthly --off
```

（关掉月报里记账应用那一段。）写进 `hub.toml`（例如 `[report."ledger/monthly"] enabled = false`），提交。卸载应用时一并删掉它的这些设置（沿用时间覆盖的做法，Claude 定）。

### 4.3 段落顺序

默认按应用名排序，留言放在最后；用户可以在 `hub.toml` 里给出顺序（例如 `[report] order = ["plans", "mail", "ledger"]`），没列出的排在列出的后面（Claude 定）。

## 5. 一份报告怎么出

报告任务触发时，agent 按定义文件的正文做（Claude 定的流程，命令名留给实现者）：

1. 运行 `cc-hub report plan <周期>`：列出这一期要出的段落（哪些是脚本段、哪些是指示段及其指示文件）和有几条留言。指示段为零、脚本段为零、留言为零时，直接回复 `NO_REPLY`，结束。
2. 对每个指示段，照它的指示写好正文，交给 cc-hub 暂存（例如 `cc-hub report put <周期> <应用>`，从标准输入读）。
3. 运行 `cc-hub report send <周期>`：cc-hub 运行所有脚本段、拼出完整报告（标题、各段、留言），写进存档并提交，用 `cc-connect send` 发到当前私聊（项目和会话取自 agent 进程的环境变量 `CC_PROJECT`、`CC_SESSION_KEY`），清空已带走的留言。它只打印"发了几段"或"没有内容、没发"，不打印报告内容，所以脚本段的输出不会进 agent 的上下文。
4. agent 回复 `NO_REPLY`，cc-connect 不再另发消息。

- 由 cc-hub 直接调用 `cc-connect send`（用户定）：这样保证 agent 不经手报告内容，也不依赖 agent 在不同 shell 里正确地把文件内容导给 cc-connect。原来"cc-hub 自己不调用 cc-connect"的原则改为只有这一个例外；登记和删除定时任务仍然由 agent 做。
- 拼好的报告为空（所有段落都没内容、没有留言）时不发，也不存档。
- 同一周期同一天已经发过时，`send` 拒绝再发（防止任务重试或手动重跑发两遍），除非加 `--again`（Claude 定）。
- 消息格式用 Markdown，交给 cc-connect 按平台渲染；超过平台单条长度时的处理留给实现者确认（cc-connect 可能自己分条）。

## 6. 留言

```
cc-hub report note <周期> --from <来源> "<文字>"
```

例子：

```bash
cc-hub report note daily --from memory-consolidate "合并了 3 条记忆，已推送"
```

- 留言暂存在总站里、不进 git（每台机器自己的，Claude 定），被下一份该周期的报告带走后清空。
- **报告关着时**：如果该周期的报告没开，留言转给下一份开着的、周期更长的报告（例如日报关着、周报开着，就进周报）；一份都没开时，`note` 不保存，退出码和输出告诉调用者"没有报告会带走它"，任务就照旧自己回复这条消息（Claude 定）。这样默认全关时，现有任务的行为不变。
- 后台任务的写法因此统一为：先 `report note`；它说会被带走，就回复 `NO_REPLY`；否则把同样的话作为回复发出。
- 出错、需要用户马上处理的事（例如推送失败、登录失效）不留言，直接回复，照旧单独发（Claude 定）。

## 7. 存档

- 每份发出的报告存成一个 Markdown 文件，例如 `reports/2026/2026-10-16-daily.md`、`reports/2026/2026-W42-weekly.md`、`reports/2026/2026-10-monthly.md`、`reports/2026/2026-Q4-quarterly.md`、`reports/2026/2026-yearly.md`（Claude 定，具体命名留给实现者），随总站提交。
- 用户回复报告里的某一条（例如"邮件那段第 3 条处理一下"）时，agent 读最近一份对应的存档来理解指的是什么。各段里条目怎么编号由应用自己决定。
- 读存档里脚本段的内容是用户在场、主动提起时才发生的；邮件应用设计 §8 里接受的剩余风险同样适用于这里（Claude 定）。
- 报告任务里写指示段的 agent 不读存档：存档里有来自邮件的脚本段，而这时是无人值守的自动运行。年度回顾之类需要回看的，用应用自己的数据（例如计划应用的打卡记录）（Claude 定）。

## 8. 现有任务和应用怎么并进来

- **总站自带的记忆整理**（`cron/memory-consolidate.md`）：正文改为按 §6 的写法：整理完 `report note daily`，会被带走就 `NO_REPLY`，否则照旧回复一段。随 `cc-hub update` 送到已有总站。
- **hub-apps 里的应用**（在本功能发布后各自改，不在本设计范围内，列在这里备忘）：
  - `ledger`：每月导账单的提醒改为月报的指示段；每个工作日的价格更新改为静默，只在失败时直接回复。
  - `plans`（还没实现，改它的设计）：早上的今日清单改为日报段；每周、每月回顾改为周报、月报段；晚上问打卡继续单独发。
  - `mail`（还没实现）：日报一段、月报一段，都是脚本段（邮件设计 §7）。

## 9. 其他改动

- `cc-hub doctor`：检查各应用 `reports/*.md` 的文件名是否是合法周期、frontmatter 是否合法；`hub.toml` 里残留的段落设置（应用已卸载）给出提示和修法（Claude 定）。
- `hub-apps` skill：应用设置时列出并请用户批准报告命令（§4.1a），提示打开它供稿的周期（§3）；应用作者文档说明 `reports/<周期>.md` 的写法。
- 设计规格里的原则相应改写（用户定）：§2 的"只搬文件，不执行"和 §8 的"cc-hub 从不执行应用提供的字符串"加上"用户在这台机器上批准过的报告命令除外"；"cc-hub 自己不调用 cc-connect"加上"发送报告除外"。
- 设计规格（`2026-09-22-cc-hub-design.md`）相应章节、README 的命令表（带完整例子）、用户文档、官网命令参考相应更新；CHANGELOG 记在 0.7.0 下（Claude 定）。
- 这项工作以发布 0.7.0 收尾，发布前先问用户；邮件应用要等它发布后才能合并（邮件设计 §11）。

## 10. 测试

- 发现供稿：总站里装的应用、各周期的 `reports/*.md`、脚本段和指示段、非法文件名和 frontmatter。
- `plan`：开关、按应用关掉的段、顺序、留言计数、全空时的结果。
- 批准：记下、命令变了失效、没批准的命令不运行而留一行说明、`reports/` 变化触发设置重跑。
- `send`：运行脚本段（成功、空输出、失败、超时）、拼装顺序和标题、写存档并提交、调用 `cc-connect send` 的参数（测试里替换掉 cc-connect）、不打印报告内容、全空不发、同日重复发送被拒。
- `note`：存、被带走后清空、周期关着时转给更长周期、全关时不保存并如实告知。
- `report section`：写入和删除 `hub.toml` 的段落而不动文件的其他内容、提交、卸载应用时清理。
- 登记命令带 `--silent`，比对时把它算进去；`language` 缺省和中英文用语。
- 真实环境验收：WSL 上装好原生 cc-connect 后，打开日报，装一个带脚本段的测试应用，确认报告到达飞书私聊、`NO_REPLY` 生效、记忆整理的留言出现在第二天的日报里。

## 11. 留给实现者

命令的确切名字和输出格式；`plan` 的 JSON 字段；环境变量名；指示段正文的暂存位置；留言暂存的位置；存档文件的命名；脚本段的超时时长；消息过长时的处理；`hub.toml` 写入时保留注释和格式的方式；`NO_REPLY` 在飞书的定时任务运行里是否生效的确认（cc-connect 1.5.0 源码里有这个约定）。
